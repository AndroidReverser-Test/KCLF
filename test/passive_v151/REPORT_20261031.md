# 普通 App 检测真机测试：准确性、覆盖与业务影响

日期：2026-10-31（Asia/Shanghai）。被测 KCLF：1.5.1，原样工作区产物 SHA-256 `fa378fcdeece9725b61d10ae89c4a4133c43c52e5200d440fd1057c9fc4450b8`。

## 验收结论

**没有达到“普通 App 全进程可靠检出，且不影响正常业务”的完整要求。** 测试成功验证了两条普通 App 权限内的真实检测方法，也实际证实了漏检和性能成本。不能把它们包装成已验收的通用反注入 SDK。

- `ctx_v151`：跳板结构与运行状态交叉校验，避免仅凭匿名 RX 或固定字节报警。可检出足够长的注入窗口；短窗口和检测线程自身被注入明显漏检。
- `x16_boundary`：受控汇编边界验证寄存器恢复；当前设备上最终两组配置的受保护线程共 24/24 用例检出，包括快速注入。但仅覆盖该线程/窗口，其他线程不自动受保护；检测晚于 payload 执行。
- 负对照未出现误报，业务校验没有错误，目标进程均存活。这只能说明本套测试通过，不能证明所有业务零误报、零崩溃或零开销。
- 50 ms 常驻扫描仍占用可观 CPU，不能满足严格的无业务影响要求。

## 环境与隔离

Android 12 / API 31 / ARM64 / Linux 5.10.66 / 4 KiB 页 / SELinux Enforcing。

测试包为本轮新安装的 `com.kclf.passive151`，non-debuggable、dumpable=0、普通 `untrusted_app`、CapEff=0、继承 seccomp=2，未添加过滤器，`no_new_privs=0`。root 只供控制端部署、KPM 管理和读取 App 已产生的日志；检测代码不使用 superkey、KPM 状态、ptrace、`/proc/self/mem` 或 payload 标记。

不修改注入器，不触碰现有业务 App。检测不暂停其他线程、不设置信号处理器、不拦截 syscall、不修改 ART/libc。最终只有测试 App 被 force-stop；进程退出后 reap、quiesce 确认 idle 才卸载本轮 KPM。设备全局 SELinux、boot_id 未改变。

## 规则与准确性约束

### ctx_v151：只读扫描，多个证据共同成立

1. 低优先级线程（nice=10）读取 `/proc/self/maps`，仅扫描可读、不可写、匿名可执行页。单周期代码扫描上限 256 KiB；超预算则轮转并记录覆盖限制。
2. 验证 136 字节恢复结构和寄存器/偏移关系，从生成代码解码 ABI 与私有页地址。识别输入没有控制器提供的地址、seed 或 payload 身份。
3. 校验独立匿名 RW 页、保存 PC 所属文件可执行区、可写 SP 区、NZCV、token 和 manual/linker ABI 关系。
4. 对关键字节、保存现场和 token 再读一次，拒绝回收/复用竞态；读取失败记为未确认，不当阳性，也不当作未注入证明。

对照故意保留了一个完全匹配当前生成器的匿名 RX 页，以及相同 RW 数据副本。RX 副本缺少有效运行上下文，因此识别结构却不报警。合法匿名 RX 函数被正常调用 1,000 次；并发随机 RX 映射创建/销毁持续进行。这比只测随机字节反例更有意义，但并未穷尽合法 JIT/上下文切换程序。

同一个解析器另经主机 ASan/UBSan 测试：4/16/64 KiB 页各 10,000 个样本全部识别且正确解码；10,000 个随机反例页零命中。主机成功不是 Android 运行期捕获率。

### x16_boundary：特定边界上的现场完整性

仅夹具自有 `guarded` 工作线程使用受控的 raw `nanosleep` 汇编边界。调用前把变化哨兵放入 x16，返回后立即保存；只接受 x16 被替换成该边界精确返回 PC 或重启的 `svc` PC。其他不一致记录 `INCONCLUSIVE`，不归为 KCLF 阳性。

这不更改 syscall 的决策或返回结果，也不 hook libc，但它不是“另开一个看门狗即可覆盖全 App”：别的线程被注入不会改变此线程的 x16。某些合法插桩/上下文修改也可能形成同样异常；规则识别的是当前实现相关的现场变化，不是恶意归因。没有证明跨 ROM、全部信号路径或任意工具链兼容。

首个 pilot 只接受 `svc` 后的 PC，真实结果是 PC-4，因此两例记录为 INCONCLUSIVE；证据保留，没有删除。按反汇编核对并修正规则后重新完整验证，不将 pilot 的未确认算作检出。

## 正常业务与负对照

负载包括 JNI/UI 动画与运算、分配和数据校验、文件读取、正常 dlopen/dlsym/dlclose、线程创建/回收，以及匿名 RX 映射 churn。无 KPM 的 10 秒压力基线和 8 段关/开扫描配对基准均无检测阳性、无未确认的 x16 异常、无业务校验错误。

50 ms 最终基线快照：201 次扫描、201 次精确模板副本拒绝、1,875 次业务循环、4,148 次映射 churn、1,937 次 guarded 调用、0 阳性/业务错误。读取竞态失败 50 次，明确作为覆盖损失记录。

96 个注入用例的已记录健康快照合计：业务循环 18,757 次、churn 44,826 次、guarded 调用 18,681 次、0 业务错误/未知 x16 变化；maps 解析失败和预算饱和均为 0。自读失败 477 次，未把读取失败当成阴性证明。快照并非精确进程退出累计值，以上是保留下来的观察量。

测试进程未观察到退出或卡死，但这不是 Android 系统完整 ANR/tombstone 审计，更不是实际业务 APK 回归。

## 性能与无干扰判断

成对基准使用同一进程，扫描关闭/开启顺序为 `0,1,1,0,1,0,0,1`。每段稳定 1 秒后计量 4 秒，每种配置累计约 16 秒；系统调频和调度仍有噪声。CPU 百分比以一个逻辑核为 100%，不是整机占比。

50 ms 优化版：

- 开启扫描的观测 CPU 为 **单核 11.17%**，平均每次扫描 CPU 5.60 ms。初版 sscanf/stdio 实现同套配对测量为单核 17.08%；优化没有消除成本。
- 工作循环吞吐：关闭约 184.06 次/秒，开启约 182.81 次/秒，约下降 0.68%。样本有限，不宣称差异有统计显著性。
- 基准各阶段 UI 帧间隔 p99 均落在 9 ms 桶上界；这不意味着没有极端帧或没有功耗影响。
- 测试中的 maps churn 持续存在；扫描与业务映射操作可能竞争内核映射锁，“不锁业务互斥量”不等于不会影响调度。

在主线程注入人为等待 200 ms 的 payload，可见约 216.6 ms 的帧间隔。该卡顿来自测试 payload 在主线程执行，不能归因于扫描器，也不能据“业务错误=0”说整次注入毫无影响。

guarded 基线计时包含两个 CPU 时钟读数等测量开销，约 4.2 us/次，仅为检查路径的粗略上界观察；没有单独验证将其集成到真实业务 syscall 边界后的总成本。不得据此宣传零开销。

### 250 ms 低频配置对照

证据：[summary.json](E:/KernelPatch/build/kclf-passive-b0ae6aab3bb8/summary.json)，[聚合结果](E:/KernelPatch/build/kclf-passive-b0ae6aab3bb8/analysis.json)。同一最终检测实现改为 250 ms 周期，32 例均确认构造执行和目标存活，13 检出、19 漏检，业务校验错误为 0。

- 受保护 guarded 线程 6/6 由 x16 规则检出；普通主线程/新旧线程快速注入 0/6、20 ms 注入 0/6、200 ms 注入 6/6；扫描线程自身 0/6；2 ms 普通线程 0/1；200 ms linker 1/1。
- 配对基准的扫描 CPU 降为 **单核 2.76%**，平均每次扫描 CPU 6.89 ms。不能把两轮不同设备调频状态下的每次耗时当作严格同比。
- 工作吞吐关闭约 183.67、开启约 184.43 次/秒，差异处于本轮噪声范围；各阶段帧间隔 p99 仍为 9 ms 桶上界。没有得到跨业务的“无影响”证明，也未测长期功耗/电量。
- 低频配置显著降低常驻成本，但 20 ms 检出降为 0/6，不能通过降低频率同时获得可靠短窗口检测。
- 此轮基线的 41 次精确模板扫描均被上下文校验拒绝，1,932 次 guarded 正常调用零异常。读取竞态失败仍作为未确认记录。

两组最终矩阵合计 128 例，24/24 受保护边界成功；**不能将这个条件成功率写成全 App 检出率**。测试由控制器在启动后固定流程注入，未随机化注入时刻，因此任何比例仅是该矩阵的观察值，不是自然业务分布上的概率估计。

## 使用建议与未通过项

目前可把这些规则作为**版本相关的风险证据和测试工具**，不应静默作为生产阻断依据。对“足够准确、可靠、正常业务无影响”的验收，仍有三个明确未通过点：普通线程快速注入漏检、观察线程自注入漏检、常驻高频扫描开销。只有结合指定业务的可插桩边界、开销预算、合法 JIT/插件清单及多 ROM 实测，才有条件评价产品适用性。

不能通过降低证据要求、把所有匿名 RX 当恶意、去掉快速/自注入用例或只报 guarded 成功来消除这些问题。
